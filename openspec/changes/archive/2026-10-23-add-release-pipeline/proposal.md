# Proposal

## Why

pane-mux can only be installed from a local checkout (`cargo install --path .`), and nothing checks pull requests or produces releases. Publishing to crates.io lets users run `cargo install pane-mux --locked`, and an automated pipeline makes shipping 0.1.0 and later versions repeatable without manual version bumps or changelog writing.

## What Changes

- Add crates.io package metadata to `Cargo.toml` (`license = "MIT"`, `repository`, `homepage`, `readme`, `keywords`, `categories`, `rust-version`) and an `include` list so only the sources, manifest, lockfile, README and LICENSE are published (`openspec/`, `tests/`, tooling files stay out).
- Add a CI workflow that runs on pull requests and pushes to `main`: format check, clippy with warnings denied, and the full test suite including the opt-in tmux integration tests against a private tmux server.
- Add a release-plz workflow: on every push to `main` it opens or updates a release PR (version bump in `Cargo.toml`/`Cargo.lock` plus `CHANGELOG.md` generated from conventional commits), and publishes any unpublished version to crates.io, then tags it and creates a GitHub Release. Because `0.1.0` is not yet on crates.io, the first merge to `main` containing this workflow publishes `0.1.0` directly.
- Add a PR-title lint workflow so squash-merged PR titles follow conventional commits, which drive release-plz version bumps and changelog entries.
- Update the README install instructions to `cargo install pane-mux --locked` and briefly document the release flow for contributors.

## Capabilities

### New Capabilities

None. This change adds packaging and CI/CD tooling only; no user-facing pane-mux behavior changes, so the change sets `skip_specs: true`.

### Modified Capabilities

None.

## Impact

- Files: `Cargo.toml`, `README.md`, new `.github/workflows/{ci,release-plz,pr-title}.yml`, new `release-plz.toml`, new `CHANGELOG.md` (generated by release-plz).
- External systems: crates.io (crate name `pane-mux`, currently unclaimed), GitHub Actions using the existing `CARGO_REGISTRY_TOKEN` secret and `GITHUB_TOKEN`.
- Repository settings already in place, done by hand outside the change: squash-only merging with "Pull request title and commit details" as the default message, workflow write permissions, and Actions allowed to create PRs. A branch protection rule requiring CI on `main` is recommended but done by hand.
- Publishing is irreversible: a published version can be yanked but never replaced, so `cargo publish --dry-run` must pass before the first merge.
- Out of scope: prebuilt binaries, Homebrew tap, crates.io trusted publishing, and end-to-end TUI tests driven through tmux `send-keys`/`capture-pane`. Each can be its own later change.
